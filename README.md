# vLLM Ascend Issue 分析工具

一个只读同步 GitHub Issue 的轻量内部工具。GitHub 数据通过公共 REST API 获取，测试分析字段仅保存在本地 SQLite 中，不会评论、订阅、修改或关联上游 Issue。

## 功能

- 首次同步全部 `vllm-project/vllm-ascend` Issue
- 每 15 分钟按更新时间增量同步
- 点击“立即同步”时执行全量校准，可补回历史分页中遗漏的 Issue
- 支持使用 GLM 对单条 Issue 和评论生成结构化分析建议，人工确认后再保存
- 支持单条/批量 AI 初筛，分类为 Bug 候选、功能需求、文档问题、使用咨询、RFC/讨论或待确认
- 初筛证据明确的非 Bug 默认隐藏，可在已过滤视图查看、确认或恢复；人工分类优先
- 支持勾选 Issue 或按当前筛选结果创建持久化批量 AI 分析任务
- 批量建议独立保存，支持进度查看、失败重试、取消和人工采纳
- “优先处理”视图只显示已分析且较可复现、价值较高的非 Doc/RFC Issue，并按复现性、价值及明确版本信息排序
- 同步 Open/Closed 状态、标题、正文、标签、作者和时间
- 支持最近一个月、状态、识别结果、价值等级和结论状态筛选
- 支持问题分析、漏测原因、补充测试等人工字段
- HTTP Basic Auth 登录保护
- “大模型配置”页签支持保存多套兼容模型配置、切换启用模型和后台连接验证
- SQLite 单文件持久化

## 本地运行

复制配置文件并修改账号、密码等配置：

```bash
cp .env.example .env
```

Linux：

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
chmod +x start.sh
./start.sh
```

后台日志默认写入 `logs/issue-tracker.log`，进程号写入 `issue-tracker.pid`。查看日志：

```bash
tail -f logs/issue-tracker.log
```

停止服务：

```bash
kill "$(cat issue-tracker.pid)"
```

Windows：

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
.\scripts\run.ps1
```

访问 `http://127.0.0.1:8080`。

## AI 建议与优先处理

### AI 初筛与人工介入

点击“批量 AI 初筛”直接打开本批 Issue 审核列表。选择已勾选项或当前筛选范围，列表展示具体 Issue，点击“开始初筛”。
初筛结束后，每条展示“确认问题 / 非问题 / 待分析 / 难以复现”和一句具体理由。可直接修改下拉框结果，翻页不丢失修改。
“难以复现”用于有异常依据但关键条件缺失、依赖不可获取或触发不稳定的情况；“待分析”表示尚不能判断异常是否成立或证据有冲突。
难以复现的 Issue 保留在列表，可按识别结果筛选，不进入优先处理视图，也不重复要求人工分类确认。
检查后在同一窗口点击“一键填写识别结果”，写入现有字段，无需再打开另一个批量填写窗口或选择批次。
默认勾选“只填写空白项”；取消勾选后，会覆盖已有识别结果。未完成、失败和结果过期的条目不填写。
关闭窗口后后台任务继续，可从任务区“查看初筛结果”重新打开同一批列表。
只读列表按每页 50 条显示，确认填写覆盖整批可用结果；填写前后内容变化的条目会跳过，避免覆盖期间的新修改。

每批保存独立的初筛结果，按批填写使用该批当时的判断，不混用后来其他批次对同一 Issue 的结论。
升级前没有批次结果快照的旧任务不会猜测填写；重新创建分析任务时，缺少快照的旧分析会重新生成一次，此后正常复用。
“确认问题”表示人工采纳为问题，不表示已实际执行并成功复现。

默认保留已有识别结果，需要替换时可取消勾选该选项。预览会固定本次要修改的条目，后续新增的筛选匹配项不会混入；
若确认前 Issue、初筛依据或已有识别结果变化，该条自动跳过，提示重新预览。
批量填写不修改问题分析、补充测试等其他字段，记录修改前后结果、操作账号和时间。

已填写的“识别结果”作为最终处理依据，统一使用表格中的识别结果筛选。
确认问题和非问题不再因 AI 初筛的待确认状态要求额外分类审核，列表直接显示识别结果。
分类仅供 AI 内部判断使用，页面不再提供分类筛选或人工分类操作。
表格不再在 Issue 标题下叠加分类、待人工确认和缺项状态，处理结论统一查看“识别结果”列。
初筛依据收进编辑窗口的可选折叠区，需要追查时再展开。

列表默认显示全部 Issue，不再提供“初筛视图”和独立的“批量填写识别结果”入口。
通过“识别结果”列筛选确认问题、非问题、待分析、难以复现，初筛审核和填写均在同一个本批列表内完成。

初筛 v3 先判断这条事项是否在报告独立产品异常，再核实复现条件。纯文档、跟踪清单和自动 CI/Nightly 失败汇总通知优先作为非问题建议，不因缺机器或启动脚本而归为难以复现。
只有有可核实的实际异常依据、且不属于上述非缺陷事项时，才判断执行入口/启动脚本、相关机器和关键配置、软件版本或提交、触发输入/步骤、实际异常和预期判据。
每项需要具体信息和可核实的正文/评论引用；“作者说是 Bug”、bug 标签、单独堆栈、维护者说已修复不能替代复现条件。
服务启动问题缺启动命令、机器或版本时，不进入可复现 Bug 候选，归入待确认并列出阻塞项。
对不需要起服务的独立脚本，接受脚本及运行方式；机器无关项可明确说明不适用，不能以“不适用”跳过执行入口、版本、触发步骤和判据。
“具备复现条件”只表示可以开始测试，不表示工具已实际复现或确认产品缺陷。
缺信息的异常报告保留在待确认中，不会当作非 Bug 删除或隐藏。已有人工分类仍优先，但不会自动成为复现证据。
提示词版本变化后需重新执行 AI 初筛，旧缓存不再复用；已有人工填写的识别结果不会自动覆盖。

点击“批量 AI 初筛”，选择已勾选 Issue 或当前筛选结果；初筛使用现有 GLM 配置、持久化后台队列和失败重试机制。
单条编辑窗口提供“AI 初筛 / 重新判断”。初筛只保存分类、原文依据、置信度、模型和提示词版本，不修改人工分析字段。
详细 AI 分析会先检查初筛；尚未初筛或内容、模型、初筛提示词变化时先初筛，明确非 Bug 则跳过详细分析。
没有被过滤的待确认项可以继续详细分析；“Bug 候选”并不等于已确认缺陷。

仅当分类为非 Bug、置信度至少 0.95、有可在发送给模型的原文中核实的引用、无异常报告且无需人工复核时，程序才给出明确的非问题建议，并跳过不必要的详细分析；主列表不会因此隐藏条目。
置信度是模型自报值，不代表分类准确率保证。标题和标签仅为线索，不按单个关键词排除。
评论读取失败、评论未读完整、上下文截断、依据缺失或存在异常报告时，不自动过滤。
工具输入被截断或评论未完整取得时，建议为待分析，不据此认定 Issue 难以复现；可搜索 `AI triage context` 查看原文长度、实际发送长度和截断标记。
输入预算默认仍为 40000 个字符（上下文 JSON 数据，不含系统提示词），正文不再固定裁成一半，评论也不再按单条 5000 字符裁剪。
优先保留完整正文和评论，超预算时先去掉历史分析与备注，再减少评论；正文自身超长才保留首尾并明确标记中间省略。
默认最多读取 100 条评论。正文/评论中的图片、脚本和日志附件链接当前不会自动下载解析，未读取附件不代表原文被截断或没有附件中的信息；关键复现资料依赖未读取附件时，建议待分析，不认定产品难以复现。
所有 Issue 都保留在数据库中，不修改或删除 GitHub Issue。

打开 Issue 可查看 AI 判断依据，通过现有“识别结果”修改处理结论，也可以批量填写。
历史分类记录保留兼容，不再要求用户额外确认分类；已填写的识别结果优先。
尚未填写识别结果时，上游更新会使旧初筛过期，被自动过滤的条目重新出现在待处理和待分析视图。

升级后首次启动会自动增加初筛字段、审核记录表和批量任务类型；旧数据保留，初始状态为未初筛。

### 测试分析

“漏测原因”保留为人工填写字段，AI 不再生成或覆盖它。“补充测试”会尽量整理 Issue 中明确给出的模型配置、A2/A3/A5 硬件、软件版本、触发场景和断言；缺失信息标记为“待确认”，不会虚构。更新后需重新批量分析，旧版 AI 记录没有复现性评级，不进入“优先处理”视图。该视图仅筛选和排序，不删除 Issue，也不修改已采纳的人工分析。筛选状态下创建批量任务时，仅分析当前视图中的 Issue。

优先级先看复现性（高、中），再看价值（高、中），然后参考明确写出的版本号与分析可信度。没有明确版本号的 Issue 不会被当作“新版本”优先；不同产品的版本号不会直接当作同一版本序列比较。Doc/RFC、非问题、低价值及复现性低或信息不足的 Issue 不出现在该视图，但仍保留在完整列表中。

## GitHub API 限额

公开仓库可以不配置 Token，但匿名 API 限额按出口 IP 共享。首次全量同步约发出 37 次分页请求，在公司代理或共享出口环境中应配置只读 `GITHUB_TOKEN`，否则可能在同步中途收到 HTTP 403。

应用仅包含 GitHub `GET /repos/{owner}/{repo}/issues` 请求，不包含写入 GitHub 的代码路径。

## 配置

应用启动时自动读取项目根目录的 `.env`。系统环境变量优先级更高，可通过系统环境变量 `ENV_FILE` 指定其他配置文件路径。

### 页面配置大模型

进入“大模型配置”页签，可选择已有配置或点击“新增配置”。填写名称、准确的模型 ID、API 基础地址和 API Key，
设置请求超时和输出 token 上限。服务需兼容 Chat Completions 流式接口；模型 ID 由实际服务提供，不预设固定模型列表。
“模型兼容参数”支持调整推理强度、选择 `max_completion_tokens` / `max_tokens`，以及关闭不受支持的 JSON 格式或 temperature 参数。

- **保存配置**：保存当前配置，不切换启用模型；若编辑的是已启用配置，新请求立即使用更新参数。
- **保存并启用**：保存后立即用于后续初筛和分析，无需重启服务。
- **启用已保存配置**：在下拉框选择配置后，切换到该配置。
- **验证模型可用性**：使用当前表单参数发起后台测试，无需先保存或启用，不发送 Issue 内容。
  页面轮询显示耗时、成功返回或上游错误（包括 504、认证失败、连接异常和 JSON 格式错误）。

测试与实际分析共用 SDK、流式调用和兼容参数，并验证返回的 `{"ok":true}` JSON。
最小请求测试通过不保证长上下文分析不会遇到网关超时。
测试在后台执行，提交接口立即返回，避免页面请求持续等待模型；同一实例最多同时运行两个连接测试。
日志搜索 `Model connection test` 或页面显示的测试编号，可关联对应请求。

初始启用“环境变量配置”，继续使用下表中的 `GLM_*` 设置。启用页面保存的配置后，这些模型连接参数以页面配置为准，
其余输入预算、评论数和批量并发配置仍使用环境变量。可随时重新启用“环境变量配置”。
编辑环境变量配置后保存会创建独立配置，不改写 `.env`。
切换配置不会影响新版本创建的批量任务，它们保留创建时的模型配置快照；升级前的任务沿用环境变量连接参数和任务记录中的模型 ID，继续支持重试。
切换 API 地址、模型或参数后，新任务不会误用其他配置的分析缓存。

密钥不通过读取配置接口回传，不放入浏览器本地存储。已有配置留空可保留密钥；修改 API 地址后必须重新填写密钥，
避免旧凭据被发送到不同服务。配置及任务快照保存在本地 SQLite 数据库中，密钥未加密，需保护数据库文件及备份的访问权限。

### 环境变量

| 配置项 | 默认值 | 说明 |
|---|---|---|
| `APP_USERNAME` | `admin` | 登录账号 |
| `APP_PASSWORD` | `admin` | 登录密码，部署时必须修改 |
| `GITHUB_REPOSITORY` | `vllm-project/vllm-ascend` | 同步仓库 |
| `GITHUB_TOKEN` | 空 | 可选只读 Token |
| `GITHUB_SSL_VERIFY` | `true` | 是否校验 GitHub HTTPS 证书；仅在可信内网代理下可设为 `false` |
| `GITHUB_PAGE_SIZE` | `100` | 每次获取的 Issue 数量；代理不稳定时可降低到 `50` |
| `GITHUB_REQUEST_RETRIES` | `3` | GitHub 请求中断后的自动重试次数 |
| `SYNC_INTERVAL_MINUTES` | `15` | 自动同步间隔 |
| `SYNC_OVERLAP_MINUTES` | `5` | 增量同步与上次成功时间重叠的分钟数，避免边界更新遗漏 |
| `GLM_API_KEY` | 空 | GLM API 密钥，仅由服务端读取 |
| `GLM_API_BASE_URL` | `https://open.bigmodel.cn/api/paas/v4` | OpenAI SDK 使用的兼容 API 基础地址，不包含 `/chat/completions` |
| `GLM_MODEL` | `glm-5.3-flash` | Issue 分析使用的模型 ID |
| `GLM_REQUEST_TIMEOUT` | `120` | GLM 请求超时时间（秒） |
| `GLM_REASONING_EFFORT` | `high` | 推理强度；Issue 根因分析默认优先保证准确性 |
| `GLM_MAX_OUTPUT_TOKENS` | `16384` | 单次分析最大输出 token 数；为推理过程和最终 JSON 预留空间，实际可用上限取决于模型服务 |
| `GLM_MAX_INPUT_CHARS` | `40000` | 单次分析最多发送的上下文字符数 |
| `GLM_MAX_COMMENTS` | `100` | 单次分析最多读取的 GitHub 评论数 |
| `GLM_LOG_PAYLOADS` | `false` | 是否在日志中记录 GLM 请求和响应正文；排障结束后应关闭 |
| `GLM_LOG_MAX_CHARS` | `20000` | 请求或响应正文在日志中的最大字符数 |
| `AI_BATCH_MAX_ISSUES` | `5000` | 单个批量任务允许包含的最大 Issue 数量 |
| `AI_BATCH_CONCURRENCY` | `3` | 批量分析 Worker 并发数，允许范围为 1～16 |
| `AI_BATCH_MAX_ATTEMPTS` | `3` | 每条 Issue 分析失败后的最大尝试次数 |
| `AI_BATCH_RETRY_DELAY_SECONDS` | `2` | 批量分析失败后重新尝试前的等待秒数 |
| `DB_PATH` | `data/issues.db` | SQLite 文件路径 |
| `PORT` | `8080` | 服务端口 |

内网代理使用自签名证书且暂时无法取得根证书时，可以关闭 GitHub API 的证书校验：

在 `.env` 中设置 `GITHUB_SSL_VERIFY=false`。

此配置仅影响 GitHub 数据同步。关闭校验后代理能够读取或修改 GitHub 返回内容，不应在不可信网络中使用，也不应同时配置高权限 `GITHUB_TOKEN`。

## 运行限制

- 只启动一个应用实例和一个 Python 进程。
- 不要使用多 worker 运行，否则每个 worker 都可能启动同步线程。
- 多实例和多人高并发场景需要将 SQLite 替换为 PostgreSQL。
