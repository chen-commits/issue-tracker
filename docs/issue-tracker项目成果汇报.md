# issue-tracker 项目成果汇报

## 从社区问题反馈到测试改进输入

> 使用方式：以下正文可直接作为汇报讲稿，建议控制在约 10 分钟。面向项目、研发和测试相关听众，突出业务价值，技术实现只保留必要说明。文末的演示建议与指标口径不计入正文时间。

## 一、项目背景与建设目标（约 1 分钟）

各位好，今天汇报的是 issue-tracker 项目的建设成果。

这个项目围绕一个具体问题展开：如何从持续增长的社区 Issue 中，及时找到值得投入的缺陷，并把问题反馈转化为测试改进的输入。

以 vLLM Ascend 为例，问题往往涉及模型、量化方式、并行策略、硬件型号和软件版本等多个维度。同样是一次推理失败，背后可能对应完全不同的环境与触发条件。重要信息还可能分散在正文和后续评论中，仅看标题很难判断问题是否有价值、能否复现，以及是否与当前测试重点相关。

因此，我们建设 issue-tracker，希望形成一套持续运行的工作流程：自动汇集问题，辅助理解与筛选，保留人工判断，并逐步沉淀可执行的测试建议。

## 二、没有这个项目时，主要有哪些痛点（约 1 分 30 秒）

第一，信息获取依赖人工，难以持续跟进。

人工浏览社区页面，需要反复翻页、搜索和查看评论。新增问题容易被关注，历史问题的补充信息、状态变化和解决进展则容易遗漏。每次专项分析，都要重新整理一遍材料。

第二，阅读投入大，筛选标准不统一。

Issue 中既有真实缺陷，也有文档反馈、功能讨论和使用咨询。真实缺陷中，又存在描述清楚、容易复现的问题，以及缺少关键配置、暂时无法判断的问题。如果逐条投入同样的精力，就会挤占高价值问题的分析时间；不同人员对价值和优先级的判断，也可能存在差异。

第三，分析结果分散，难以复用。

已有结论可能保存在个人表格、文档或聊天记录中。换一个人接手，往往需要重新阅读原文。哪些问题已经确认、哪些需要补充测试、哪些还在等待版本支持，也缺少统一的查看入口。

第四，社区反馈与测试工作之间缺少衔接。

发现一个有价值的缺陷后，测试人员仍需重新提取模型配置、硬件环境、软件版本和复现步骤。问题被看过，并不意味着它已经成为可以验证的测试场景。

## 三、目前已经建成哪些能力（约 2 分钟）

针对这些痛点，项目目前形成了四项核心能力。

第一项是持续的数据汇集。

系统支持首次全量同步、默认每 15 分钟增量同步，以及手动全量校准。既能跟进新增和更新的问题，也有补齐历史遗漏的手段。同步更新社区侧信息，人工填写的分析内容单独保留，让持续跟进与分析积累可以同时进行。

第二项是面向分析工作的统一台账。

系统支持按日期、状态、标签、价值等级、识别结果和版本等条件筛选，也可以记录问题分析、补充测试、版本支持情况及是否闭环。分析结果能够保存在同一个入口，并按当前筛选范围导出 Excel，便于专项评审和阶段汇报。

第三项是 AI 辅助的结构化分析。

系统已接入 GLM 模型，结合 Issue 正文和评论，生成中文摘要、价值判断、可能根因、建议动作及补充测试等内容。AI 建议由人工检查后采纳，最终结论仍由分析人员负责。

这里有一个明确的设计取舍：“漏测原因”保留为人工填写。因为只看社区 Issue，无法知道内部测试实际覆盖了什么，不能让模型据此推断内部漏测原因。

第四项是可批量执行、可持续跟踪的分析任务。

用户可以勾选指定 Issue，也可以按当前筛选结果发起批量分析。任务支持可配置并发、进度查看、失败重试、取消，以及服务重启后的任务恢复。这样，分析工作既适用于单条深挖，也能支持阶段性的集中梳理。

## 四、项目如何帮助我们找到更值得处理的问题（约 1 分 30 秒）

在具备批量分析能力之后，下一步关键是让结果帮助我们分配精力。

项目增加了“优先处理”视图，结合复现性、价值等级和明确的版本信息进行筛选与排序。文档、RFC、非问题，以及低价值或复现证据不足的问题，不进入这个视图；完整数据仍然保留，便于后续回看。

这里的复现性评价，依据的是 Issue 已经提供的步骤、配置、日志和触发条件。模型提出一条补测建议，并不代表问题已经被验证能够复现。版本信息也只作为辅助依据，不能把版本号较大直接等同于问题已经修复。

对于进入分析范围的问题，“补充测试”会尽量整理成测试人员能继续执行的材料，包括模型名称、精度和量化方式、TP/PP/EP 等配置，A2、A3、A5 等硬件信息，以及 CANN、torch_npu、vLLM 和 vLLM Ascend 的版本。

同时，建议中会尽量明确触发请求、并发、序列长度、预期结果和验证断言。原文没有提供的信息，会标为“待确认”，帮助分析人员知道下一步需要补采什么。

## 五、项目已经带来哪些价值（约 1 分 30 秒）

首先，工作方式从临时查找转向了持续积累。

问题数据能够持续更新，人工分析能够保留。阶段分析可以在已有结果上继续推进，减少重复收集和重复阅读。

其次，专家精力可以更集中地用于判断和验证。

系统承担数据汇集、筛选和初步归纳，AI 提供待审核的结构化建议。分析人员可以把更多精力放在确认问题价值、核实根因，以及设计和执行测试上。

第三，分析结果更便于共享和复用。

统一字段让不同问题能够放在同一框架下查看，也方便团队交接和专题讨论。社区反馈中的模型、硬件、版本和触发条件，开始以更适合测试工作的形式沉淀下来。

第四，项目已经形成了进一步改进质量管理的基础。

目前已经打通了从问题汇集到分析建议、人工采纳和状态记录的流程。实际复现、用例入库和 CI 执行仍需后续衔接，但已经有了统一的数据入口和分析载体。

关于成效，我们目前可以明确汇报的是这些能力已经落地。具体节省多少工时、AI 建议有多高的采纳率、最终转化了多少测试用例，还需要通过运行数据持续量化，不宜直接给出未经验证的提升比例。

## 六、后续优化方向（约 2 分钟）

第一，优先验证 AI 分析是否准确、是否有用。

计划选取有代表性的 Issue，由人工建立评审样本，分别评价摘要准确性、价值判断、复现性判断和补测建议的可执行性。重点关注两个问题：有没有漏掉真正重要的缺陷，以及推荐出来的问题能不能推进实际验证。再根据评审结果迭代提示词和筛选规则。

第二，补充更可靠的分析依据。

逐步引入经过确认的版本配套信息、已验证的历史案例，以及关联 PR 和修复记录。对重要判断增加原文依据和信息缺口说明，让分析人员更容易核查结论。涉及内部测试覆盖时，再接入实际用例信息，由人员确认漏测原因。

第三，推动高价值 Issue 转化为回归测试。

围绕筛选出的重点问题，建立“人工复现、提炼最小用例、评审入库、跟踪回归结果”的流程。模型可以辅助整理复现脚本和测试草案，具体执行需要结合可用的硬件环境和评审要求推进。

第四，完善运营指标与协作能力。

持续跟踪分析耗时、建议采纳率、有效复现率、测试用例转化量和模型调用成本。随着使用范围扩大，再完善负责人、处理记录、权限和备份等能力，并根据实际规模升级数据存储与任务调度。

## 七、结束语（约 30 秒）

issue-tracker 当前的成果，是围绕社区 Issue 建立了一个能够持续更新、统一分析、辅助筛选和沉淀结果的工作平台。

下一阶段，我们会把重点放在分析质量和测试转化上：让推荐结果更可信，让补测建议更可执行，并用实际复现和回归用例来验证项目价值。

我的汇报到这里，谢谢大家。

## 附：现场演示建议（不计入正文时间）

如需保留 1 分钟演示，可适当压缩第三、第五部分，依次展示：

1. 按日期和状态筛选，说明问题范围可以快速收敛。
2. 打开一条已有完整建议的 Issue，展示模型配置、环境信息和复现条件。
3. 展示 AI 建议的人工采纳入口，说明最终判断的责任归属。
4. 切换“优先处理”，展示优先级及推荐理由。
5. 展示一个已完成的批量任务，说明进度、失败项和重试能力。

演示优先使用已完成的分析记录，避免现场等待模型返回。不要展示 API 密钥、内部地址或含敏感内容的日志。

## 附：建议补充的成效指标

| 指标 | 建议统计口径 | 用途 |
|---|---|---|
| 数据覆盖情况 | 本地同步数量与同仓库、同时间点、同筛选范围的上游 Issue 数量核对，排除 PR | 评估同步完整性 |
| 人工分析耗时 | 对相近复杂度样本，比较纯人工与 AI 辅助后的人工投入，包含审核时间 | 量化效率收益 |
| AI 建议采纳率 | 已审核建议中，可直接或修改后采纳的占比；分字段统计 | 评估建议质量 |
| 优先推荐有效率 | 已人工核验的推荐 Issue 中，被确认值得投入验证的占比 | 评估筛选价值 |
| 有效复现率 | 实际投入复现的问题中，能够稳定复现的占比；同步记录失败原因 | 评估复现性判断 |
| 测试转化量 | 经评审新增或改进的回归用例数量，关联来源 Issue | 评估测试贡献 |
| 分析成本与稳定性 | 单条分析调用成本、任务成功率、重试次数和完成时长 | 评估运行效果 |

没有统计数据时，可直接使用正文中的定性表述。历史对话中的 Issue 数量不应作为当前项目规模；汇报前应按实际运行数据核实。AI 生成建议、人工确认、实际复现和用例入库属于不同阶段，汇报时分别统计。
